# Private llama.cpp ROCm backend

Issue 10 is implemented only through the safe pre-benchmark gate. The production
router is disabled. No model or key is selected, downloaded, or generated by
this repository.

## Verified package and b9190 semantics

`packages/llama-cpp-rocm.nix` overrides the llama.cpp package from the currently
pinned nixpkgs revision. Evaluation fails unless all of these remain true:

- llama.cpp version is `9190`;
- `GGML_HIP` is enabled;
- `CMAKE_HIP_ARCHITECTURES` contains only `gfx1150`;
- `clr`, `hipblas`, and `rocblas` are all ROCm `7.2.3`.

Pinned llama.cpp source does **not** define an HIP UMA CMake option. Its
`docs/build.md`, in the HIP "Unified Memory" section, prescribes the runtime
setting `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` for a Linux integrated GPU. The
service sets exactly that variable. It does not set or claim `HSA_XNACK`,
`HSA_OVERRIDE_GFX_VERSION`, or a hardware runtime result.

Pinned source also establishes the idle behavior rather than requiring a custom
controller:

- `common/arg.cpp` defines `--sleep-idle-seconds` for the server;
- `tools/server/server-context.cpp` calls `destroy()` on entry to sleeping
  state; `destroy()` resets `llama_init` and clears/frees the target context,
  model pointers, multimodal context, and batch;
- `tools/server/README.md`, "Sleeping on Idle", says model and KV-cache memory
  are unloaded and the model reloads on the next task;
- the router reports a child as `sleeping` and proxies the next request to wake
  it.

Therefore b9190's native `--sleep-idle-seconds 1800` is the smallest reliable
implementation. A separate unload controller would duplicate working upstream
behavior. The disposable VM compresses the timer while checking the configured
1800-second contract; it does not claim ROCm runtime behavior.

`--api-key-file` reads one non-empty key per line in b9190's `common/arg.cpp`.
The service receives Alex's and Andreea's files separately through systemd
credentials, validates that they are distinct token-shaped values, and writes a
mode-0600 two-line file in `/run/llama-router`. Key values never enter Nix, the
store, or command-line arguments. Request bodies are debug-level source logs;
production uses `--log-disable`, so neither request nor prompt bodies are
journaled. Metrics stay enabled on the private endpoint.

## Exact disabled and ready interface

The default is:

```nix
balaur.sharedServices.llama.readiness = {
  ready = false;
  modelPresetFile = null;
  ownerApiKeyFiles = {
    alex = null;
    andreea = null;
  };
  memoryHighBytes = null;
};
```

There is no `llama-router.service`, service user, listener, firewall opening, or
Caddy route in that state. Missing files cannot break evaluation or the host
build.

After all human gates below, the shape is:

```nix
balaur.sharedServices.llama.readiness = {
  ready = true;
  modelPresetFile = "/srv/models/<approved>/router.ini";
  ownerApiKeyFiles = {
    alex = "/run/balaur-secrets/owners/alex/llama/<runtime-name>";
    andreea = "/run/balaur-secrets/owners/andreea/llama/<runtime-name>";
  };
  memoryHighBytes = <measured-peak-plus-reviewed-margin>;
};
```

The preset validator requires exactly one local GGUF path under `/srv/models`,
rejects startup preload and network/Hugging Face model sources, and resolves the
model path beneath the mounted dataset. This file is a benchmark-approved
manifest, not a repository default. `MemoryHigh` must be derived from measured
peak inference memory plus a reviewed margin while preserving the 10 GiB host
headroom gate. It is a soft throttle for optional inference; there is deliberately
no `MemoryLow` protection competing with Jellyfin and no guessed hard
`MemoryMax`.

The resulting command is the pinned b9190 interface:

```text
llama-server --host 127.0.0.1 --port 8081 --offline \
  --models-preset /srv/models/<approved>/router.ini \
  --models-max 1 --models-autoload --parallel 1 --ctx-size 32768 \
  --cache-type-k f16 --cache-type-v f16 --n-gpu-layers all --fit off \
  --cache-prompt --metrics --no-slots --no-ui --log-disable \
  --sleep-idle-seconds 1800 --api-key-file /run/llama-router/api-keys
```

The unit requires `/srv/models` to be a mount point, orders after local
filesystems, and only reads that mount. It has explicit `/dev/kfd` and
`/dev/dri/renderD128` access. CPU/IO weight is 100 versus Jellyfin's 200, and
inference receives a higher OOM score. This is not represented as GPU
preemption: the explicit GPU workload policy is one loaded inference model and
one slot, no second inference workload, with production enablement rejected if
the physical Jellyfin contention gate fails.

## Network and issue 12 gate

The raw API binds only `127.0.0.1:8081`; systemd denies non-loopback network
access, the global and trusted-interface firewalls do not open 8081, and no raw
API Caddy route exists.

Issue 12 implements one source-restricted forwarder on each owner's private
host-side container address, passes only that owner's key into the matching
container, and enforces exact source/destination firewall rules. The forwarders
exist only when both the llama benchmark gate and that owner's personal-stack
gate are ready. There is no broad bridge listener or household Caddy ingress;
production readiness remains blocked until the physical benchmark, owner keys,
and container isolation checks pass.

## Human gates

1. Run all four physical benchmarks in
   [`research/llama-benchmark-runbook.md`](research/llama-benchmark-runbook.md).
2. Record a passing candidate's publisher provenance, exact local filename,
   SHA-256, measurements, reviewed thermal limit, and benchmark-derived memory
   target. Do not infer any of these from the build tests.
3. Human-review exactly one local router preset. Selecting it is an explicit
   production decision, not an action performed by the harness.
4. Complete age/sops onboarding. Generate separate strong API keys locally and
   encrypt each under its owner's policy; do not reuse VM fixture values.
5. Complete issue 12 stable owner container addressing, per-owner forwarding,
   key mounts, and cross-owner/firewall tests.
6. Rebuild and repeat listener, mount-loss, idle-release, memory-headroom,
   thermal, GPU-reset, and Jellyfin contention checks on the physical host.
